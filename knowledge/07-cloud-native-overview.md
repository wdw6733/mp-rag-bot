# 云原生概览

## 是干什么的

云原生是一套在云上构建和运行应用的方法，核心是：应用拆成小服务、用容器打包、按需自动伸缩、出了故障自动恢复。目标是让应用跑得稳、上线快、资源用得省。

常说的云原生技术栈包括容器、Kubernetes、微服务、服务网格、可观测性、持续交付。它们不是必须全用，而是按需组合。

## 怎么工作

### 微服务：拆小、独立部署

把一个大应用拆成多个小服务，每个服务只干一件事，有自己的代码、数据和发布节奏。服务之间通过网络接口调用。一个服务挂了、升级了，不影响其他服务。代价是服务多了，调用链变长，排查问题要靠链路追踪。

### 容器与编排：打包一次，到处运行

容器把应用和依赖打在一起，开发、测试、生产跑同一份镜像。Kubernetes 负责调度、扩缩容、自愈：副本不够自动补，节点挂了自动把 Pod 挪到别的节点，流量大了自动加副本。

### 声明式 API：说出想要的状态

K8s 的管理方式是声明式的：你写一份 YAML 说“我要 3 个副本、这个镜像、这个端口”，控制面负责把现状变成你要的样子，中间差多少就补多少。不用一步步下命令去启动、停止、检查。

### 服务网格：把通信的活抽出来

服务之间调用要处理重试、超时、熔断、流量切分、互相认证，这些逻辑写进每个服务很重复。服务网格把这部分抽出来，放到每个 Pod 旁边的 sidecar 代理里统一管，业务代码不用关心通信细节。小规模用不上，大规模才划算。

### 可观测性：日志、指标、追踪

分布式系统出了问题，不能靠猜。要有三样东西：日志看应用说了什么，指标看系统健不健康，链路追踪看一次请求经过了哪些服务、卡在哪一步。三者结合才能快速定位故障。

### 持续交付：改动快速上线

代码提交后自动构建镜像、自动跑测试、自动部署到环境，人工只做审批和确认。配合滚动更新和灰度发布，新版本先给一小部分流量，确认没问题再全量，出了问题快速回滚。

## 动手例子

一个最小的云原生应用长这样：代码在 Git 仓库，CI 构建镜像推到镜像仓库，Kubernetes Deployment 声明 3 个副本，Service 对内暴露，Ingress 对外提供域名，监控看指标、日志看输出。

本地先把流程跑通，再上集群：

```bash
docker build -t my-app:1.0.0 .
docker run -d -p 8080:80 my-app:1.0.0
```

镜像在本地能跑起来，再写 Deployment 的 YAML 部署到 K8s：

```bash
kubectl apply -f deployment.yaml
kubectl get pods -l app=my-app
kubectl get svc my-app
```

`kubectl apply` 是声明式管理的入口：改 YAML 再 apply 一次，集群就会向新状态靠拢。

## 常见坑

- **为了微服务而微服务**：服务拆得太细，调用链长、运维成本高，小团队反而更慢。先从单体加模块化做起，真的到了瓶颈再拆。
- **只上容器，不上编排**：几台机器手写脚本管容器，数量一多就管不过来。容器数量超过一台机器能装的，就该考虑 K8s。
- **没有可观测性就上生产**：服务一多，故障定位全靠猜。日志、指标、追踪至少要有一样能用，再上生产。
- **配置和密钥混进镜像**：镜像推到仓库，密钥就跟着走了。配置用 ConfigMap，密钥用 Secret 或专门的密钥管理，镜像里只放代码。
- **忽略成本**：自动扩容不设上限，流量一涨账单跟着涨。给扩容设上限、给资源设 limits，定期看用量。
- **把云原生当成换工具**：容器、K8s 只是工具，核心是开发、测试、上线的流程要跟着变。工具换了、流程还是老样子，效果出不来。
